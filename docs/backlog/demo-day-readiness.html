MedAssist · plan of record

Getting one flow demo-ready

Booth format. A visitor walks up, hears the background, then watches the whole MedAssist journey run live: a new patient opened in the back office, a Telegram link landing on a real phone, and the visit unfolding step by step on one route, one procedure, one department — with the real Wolfson photos. The pitch is that on this route it already works, and the rest of the hospital is duplication rather than invention.

What changed about the priorities

The edge-case backlog is parked. The flow is the product now.

Decided

M2, the offline service worker, is dropped — along with the rest of the edge-case queue — until the demo flow itself is presentable. Nothing in that queue is visible during a walkthrough. Effort goes to the journey a visitor actually sees.

Hosting is settled: laptop plus our own hotspot. An AWS deploy is a stretch goal, attempted only if the flow is solid with days to spare. Deploying competes directly with fixing the flow, and there are only twelve days.

Every navigation image in the database is a placeholder — example.com/a.jpg or placeholder.example.com/step-N.jpg. There is no real route in the product. The seeded one has five steps; the Figma route has seven, and its photos are sitting in a folder outside the repo.

Opening the back office in front of a visitor today shows a landfill of test-route-1787405314453 rows. That gap between the product and the Figma story is content, not architecture — which is why it is fixable in the time available.

The blocker nobody has hit yet

Found while planning. It only shows up on a real phone.

Highest risk in the plan

The API builds public image URLs from the storage endpoint. Configured for local development, that endpoint is localhost:4566 — so the phone receives image URLs pointing at its own localhost and every navigation photo renders broken. The magic-link address in the Telegram message and the API address the app calls have exactly the same problem.

All three are configuration values, not code, so they are cheap to fix — but only if we find them before demo day instead of on stage. This is what Phase 3 exists for.

The one that would have gone off on stage

Found after Phase 0 shipped, fixed the same afternoon.

Caught before the booth

The magic-link message is queued in Redis after the database work commits, so wiping the database left the queued messages untouched. 451 of them had piled up. Starting the worker with sending switched on would have drained every one to a real phone — a burst of messages, most of them carrying tokens that no longer resolve to anything but an error page.

The reset now clears the queue too. One reset means exactly one pending message, which is the whole point of having a reset ritual.

The plan

Four phases, strictly in order. Phase 0 is what makes Phase 1 meaningful — walking the flow on a swamp database tells us nothing about what a visitor will see.

Phase 0 · done

Clean slate with real content

  • A reset command. One script that wipes every data table and reseeds. This becomes the booth ritual: run it between visitors so every walkthrough starts identical, and once before demo day so the junk department and the 54 test routes are gone. Guarded so it refuses to run against anything but the development database.
  • Real photos in the real route. The route grows from five steps to seven, matching the prototype. The seven Wolfson photos get committed into the repo and uploaded through the same path a staff upload uses, so they are compressed and stored identically.
  • Instruction text per step is drafted from the photos and shown for approval before anything is committed — it is patient-facing copy.
  • The department becomes real. Address, parking, transit and map position are all fields the patient sees and all currently empty, which leaves the arrival screen looking half-built.

Shipped. The database now holds one patient, two departments and two routes, and the demo route carries all seven real photos. The photos turned out to end at מחלקת עיניים, not cardiology, so the demo department, procedure, checklist and forms are all ophthalmology now — cardiology stays seeded because twelve test files look it up by name. Three suites green: 83 API, 18 patient app, 15 back office.

Four pre-existing bugs surfaced and were fixed on the way: re-seeding a live database left the demo appointment with no forms at all, and the bulk-delete spec had three separate faults that meant it had never run green.

Phase 1 · done

Walk the flow and write down every break

On the fresh database, in a real browser, exactly as demo day runs it:

  1. Staff logs in to the back office
  2. Creates the appointment, sending the link immediately
  3. Telegram message arrives
  4. Open the link — entry screen, then arrival info
  5. Checklist: tick items, watch the state hold
  6. Forms: upload a photo, type a field, sign a consent, continue
  7. Navigation: seven steps, real photos, confirm each
  8. Waiting: queue position and live updates
  9. Back office: patient in the queue, stations advancing, patient called in
  10. The side dishes — the ER track and the admin configuration screens

Output is a ranked defect list: every break, every rough edge, every place the story stalls, each tagged blocker, visible, or cosmetic. No fixing during the walk — observing and fixing at once is how a walkthrough becomes a three-hour tangent.

The flow works end to end. Steps 1 to 9 were walked in a real browser: the back office created the patient, a real Telegram message was sent and delivered, the link opened, the checklist showed all eight eye items, the forms gate correctly refused to move on with documents missing, all seven Wolfson photos rendered in order through to the reception desk, the waiting screen showed a live queue position, and the patient reappeared in the back office as waiting. A visitor could be walked through this today.

One blocker. The procedure field staff type when creating a patient is free text, and the suggestion list the app itself offers does not match any real template — picking its own suggestion produces a patient whose checklist does not exist. That is the first thing a visitor watches being typed. Below it sit several visible rough edges: the patient is shown a raw English slug, the forms picker offers every procedure's paperwork at once, nothing is attached unless staff ticks it, and long Hebrew labels break the row layout.

The ER track and the admin configuration screens have not been walked yet.

Phase 2 · next

Fix, ranked by what a visitor sees

Work the list top down. Blockers, then visible problems, then cosmetics only if time remains. Four issues are already known and likely to surface: a session expiring mid-upload on the admin screens, no way to create or delete a department, form templates that cannot be edited once created, and a checklist reminder that is written but never actually sent.

Explicitly out of scope unless the walkthrough proves otherwise: the offline service worker, the notification-cap edge cases, the database connection-pool issue, and the missing API test coverage. None of them appears in a demo.

Phase 3

Network dress rehearsal on the real phone

  • Order matters: set the addresses first, then reset. The photo URLs are written into the database when the route is seeded, so changing the address afterwards does nothing to rows that already exist.
  • Bring the stack up bound to the hotspot address rather than localhost — including the storage endpoint, the one everybody forgets.
  • Already checked: storage is published on all interfaces, so the hotspot address reaches it from both the laptop and the phone. This stays a configuration change; no code needed.
  • Send a real Telegram link to the actual demo phone, over the actual hotspot, and run the whole journey on it: images load, uploads work, the camera opens, the signature works with a finger.
  • Rehearse the reset-between-visitors ritual end to end at least twice.

This is where the demo fails if it is going to. It happens early enough to fix, not the night before.

Running it

Three terminals. The worker is not optional — without it no Telegram message is ever sent.

docker compose up -d
doppler run -p medassist -c dev -- pnpm --filter api db:reset-demo

doppler run -p medassist -c dev -- pnpm dev                 # api + both frontends
doppler run -p medassist -c dev -- pnpm --filter api worker # required for Telegram
Order matters at the booth

The test suites are what put the junk department and the 54 routes into the database in the first place. Run the tests, then reset, then demo. Never the other way round.
