M1 — Logout doesn't revoke the staff session Done

Branch fix/logout-session-revocation → merged --no-ff into feat/final-figma-redesign (b6d3701)

  1. Fix applied. logout() now calls addToRevocationSet (the correctly-prefixed function) instead of writing to the wrong Redis key. Dead duplicate verifyToken removed.
  2. Code review dispatched (/superpowers:requesting-code-review). Verdict: production fix correct, verified live — but the regression test was a false negative. Playwright's client auto-clears its cookie on logout's Set-Cookie response, so the "same cookie after logout" check never actually replayed the revoked token.
  3. Test rewritten to replay the raw token explicitly (the real threat model: a stolen/cached cookie). Verified in both directions by swapping in the pre-fix file contents — fails pre-fix (200), passes post-fix (401).
  4. Second bug found while verifying, unrelated to the code review: running the new test alongside others caused 3 unrelated failures. Root cause — staff JWTs had no unique-per-login ID, so two logins to the same account in the same second produced the identical token string; logging out of one silently revoked the other. Invisible before this fix (logout didn't revoke anything for real), a live cross-session bug now that it does.
  5. Scope decision (asked user): folded into M1. Added jti: randomUUID() to the JWT payload so every login's token is unique regardless of timing.
  6. Verified: full tests/api suite — 63/63 passing — after the jti fix.
  7. Shipped. Committed (28b4092), merged, pushed. Worktree removed.

E3 — Two devices opening Waiting at the same moment Done

Branch fix/e3-waiting-upsert → merged --no-ff into backlog-fixes (03d111f)

  1. Fix applied. The waiting-queue row is created lazily on first load, but appointment_id is UNIQUE and the insert had no ON CONFLICT — whoever lost the race got a raw duplicate-key 500. The arrival path in navigation.service.ts already wrote this same insert correctly; the two sibling paths now match.
  2. Scope past the ticket, deliberately. Restructured so the race loser re-reads the winner's actual row (real status, wait estimate, broadcast fields) instead of a hardcoded 'waiting' plus nulls. That also closed an unguarded crash: an appointment with no matching row used to throw a 500, now returns a clean 404.
  3. Reproducing it was the hard part. Firing requests in parallel never triggered it — 10 Playwright requests on one connection, 10 on separate connections, 20 raw fetches: all serialized (20 requests in 64ms, a straight line). The collision window is roughly a millisecond wide, and volume does not reliably land in it.
  4. Test made deterministic instead of lucky. A second database connection opens a transaction, inserts the row, and holds it uncommitted; the real request then goes in flight and blocks on the unique index. The race happens on purpose, every run.
  5. Verified both directions: fails against pre-fix code with the exact 500, passes after. Full tests/api suite — 66/66.
  6. Shipped. Committed (acb57dc), merged, pushed. Worktree removed.

E13 — A failed checklist save erased a later tap Done

Branch fix/e13-checklist-rollback → merged --no-ff into backlog-fixes (a720116)

  1. The bug. Ticking a box updates the screen immediately and saves in the background. If that save failed, the screen was restored to how it looked when the tap started — so any box the patient ticked while the save was still in flight got silently un-ticked too.
  2. Fix applied. A failed save now undoes only its own box, and each tap reads the current state rather than a stale snapshot, so a fast second tap builds on the first.
  3. Same test trap as E3, different shape. The first version of the test failed the save instantly — which resolved before the second tap even happened, so the two never overlapped and the test passed against the broken code. Holding the failure open for 800ms puts the taps in the order that actually breaks it.
  4. Verified both directions, and re-checked red against the unfixed code after the test was restructured — not just once at the start.
  5. Known gap left open on purpose: after an undo, the server still holds the tick the screen reverted; the next successful save reconciles it. Properly fixing that means re-sending after failure, which risks a retry loop. Folded into the offline work (M2), which has to solve queue-and-replay anyway.
  6. Shipped. Patient PWA suite 13 passed / 1 pre-existing skip, typecheck clean. Committed (e329678), merged, pushed. Worktree removed.

E11 + E12 — Network failures the patient never saw Done

Branch fix/e11-e12-network-error-paths → merged --no-ff into backlog-fixes (a9bf7ca)

  1. Two pages, one defect. Both swallowed connection errors, so they were done as a pair in one branch. On Navigation, tapping "אני כאן" with a dropped connection stopped the spinner and showed nothing at all. On Waiting, a failed first load left the patient on "טוען מצב תור..." with no indication anything was wrong.
  2. Design agreed before any code was written. Navigation shows the error inline under the button, so the step stays on screen and the patient can just tap again. Waiting swaps the loading line for an error line, reusing the error text style already used elsewhere.
  3. No retry button, on purpose. The Waiting page already re-checks on a timer, so it recovers on its own once the connection is back — and the patient app has no retry button anywhere today. Adding the first one was not worth it for a screen that heals itself.
  4. Last known state is kept. Once the queue has loaded, a later failed check leaves the real queue position on screen rather than replacing it with an error.
  5. Two harness traps found while testing. Blocking "waiting" requests also blocked the page itself from loading, and the navigation screen opens on the "getting to the hospital" view — the step confirm sits behind it. Both cost a round of red tests before the specs were right.
  6. Shipped. All four specs verified red pre-fix, green after. Patient PWA suite 17 passed / 1 pre-existing skip, typecheck clean. Committed (b4e4537), merged, pushed. Worktree removed.
  7. Follow-up correction (542228e): the first pass sent every confirm failure to the new inline message, including rejected requests like an expired link. Those are not fixed by tapping again, so they go back to taking over the page. Inline is now reserved for connection failures, which is what was actually agreed.

E6 + E10 — Staff permissions on the back office Done

Branch fix/e6-e10-staff-authz → merged --no-ff into backlog-fixes (b869c2c)

  1. E6 turned out not to be a hole. The audit read it as admin pages protected only by accident of configuration order. Probing the running API first says otherwise: with no login they already return 401, and to a non-admin staff member 403. Nothing was exposed. Two of the five admin areas simply didn't state their protection, leaving it dependent on setup order.
  2. Fixed anyway, cheaply. Both now declare it like the other three. The accompanying test passes against the old code too — it exists to make a future reshuffle fail loudly, not because anything was broken. Worth being clear about that rather than claiming a vulnerability was closed.
  3. E10 was real. Adding, reordering, or completing a patient's treatment stations had no department check at all — a staff member in one department could act on any other department's patients. The queue screens already prevent this; stations were simply missed.
  4. Same rule now applies: staff act only within their own department, admins are unrestricted, and anything out of scope reads as "not found" rather than "forbidden", so it doesn't reveal that the patient exists.
  5. Sending a patient onward to another department still works — that's routine, and the check is on which department owns the patient, not where they're being sent. Covered by a test so it can't be tightened by mistake later.
  6. Shipped. The three cross-department tests verified red pre-fix, green after. Full API suite 83/83, typecheck clean. Committed (1c1e820), merged, pushed. Worktree removed.
  7. Follow-up (e569de4): reviewing this turned up four copies of the same permission-scope logic across the code, and they disagreed with each other about whether an admin assigned to a department counts as an admin. Consolidated into one, keyed on role. Not reachable today, settled so it stays that way.

M4 — Medical detail in calendar exports Won't fix

Closed by product decision, 2026-08-22. Not deferred for time — decided against.

  1. The decision: the "add to calendar" buttons stay exactly as they are. Being able to save "you need to fast" or "go get blood tests" into your own calendar is worth a small amount of medical detail leaving the app. The patient chooses to tap it.
  2. The audit called this a constitution violation. It isn't. The constitution says links "contain no medical data in the URL" and that medical detail is never included in a Magic Link URL or written to logs. Both are scoped to Magic Links. The project's summary of that rule shortens it to "no medical data in URLs", which is what made this look like a breach. A Google Calendar link the patient deliberately opens is not a Magic Link.
  3. So no constitution amendment is needed, and the hard rules are untouched: nothing medical in Magic Link URLs, nothing medical in logs.
  4. Recorded so it does not come back as an open finding in a future audit.
